# 多月份备份与选择性恢复设计方案

日期：2026-10-09
项目：MTEmpHub
状态：用户已确认核心需求；本文新增的技术决策作为实施建议，实施前阅读并核对。当前仅编写文档，尚未修改业务代码或数据库。
配套实施计划：`docs/design/2026-10-09-monthly-backup-plan.md`

## 1. 目标与已确认需求

把现有单月账套导入导出改为多月份备份与选择性恢复。用户所说“和钉钉一样”指产品使用体验，不是本项目的钉钉同步入口；具体行为以本文件为准，不假定钉钉产品的实现。

1. 导出月份支持多选，一个 ZIP 包含多个所选月份。
2. 导出内容默认全部勾选，用户可以取消。
3. 导出当前完整部门、人员、班次等资料，不局限于当月有业务记录的人员。
4. 账号备份包括密码哈希、账号状态、角色、页面权限及人员/部门授权关系；没有明文密码。
5. 导入自动识别月份和已包含的内容，允许只恢复部分月份、部分类别。
6. 展示新增、冲突、系统独有、一致四种差异以及字段差异。
7. 备份独有默认新增；冲突默认采用备份值；系统独有默认不保留；支持选择保留系统值或跳过新增。
8. 支持逐条选择、任意多选和批量操作，不限于处理全部冲突。
9. 未选择月份、类别不能被隐式修改。跨月及年度资料单列，显示影响范围，由用户明确选择恢复。
10. 当前人员入离职、部门新增解散及班次变更，不能改变过去月份的业务数据、人员归属、报表展示和计算所依赖的资料。
11. 恢复确认页列出最终新增、更新、移除/删除及跨月影响；失败时整次恢复回滚。
12. 后续业务代码增加或更改数据时，备份、差异预览、恢复和兼容处理必须同步更新。

## 2. 本次代码核查结论

核查是静态阅读，没有操作实际备份、恢复或迁移，没有运行测试。

| 文件 | 当前行为 | 与目标的差距 |
| --- | --- | --- |
| `services/account_set_backup_schema.py` | 显式 DATASETS、字段、自然键及 scope；格式版本为 1 | 缺账号、月度快照、类别完整性描述及兼容转换 |
| `services/account_set_backup_service.py` | collect_backup/export_backup 接受单个账套 ID；共享资料按业务关联收集 | 不支持多月和当前完整资料 |
| `services/account_set_restore_service.py` | 单月预览，冲突默认 system，少数类别允许删除，共享独有记录不进入差异 | 默认策略、选择范围和多月事务需要扩展 |
| 同上 | 菜票冲突禁止覆盖，资金关系存在额外一致性校验 | 必须定义恢复替换与依赖一致性，不能仅放开限制 |
| `models/daily_record.py`、`models/monthly_report.py` | 通过 emp_id 引用当前 Employee | 没有完整、独立的月度资料快照 |
| `models/employee.py` | 部分业务关系为 delete-orphan 级联删除 | 不能物理删除人员来退出当前资料 |
| `models/meal_ticket.py` | 明细保存工号、姓名、部门名称快照 | 有可参考的历史展示基础，但不是完整历史隔离 |
| `routes/query_core.py`、`services/manager_attendance_service.py` | 多处使用当前姓名、部门、是否管理人员和离职状态 | 恢复当前资料可能改变旧结果或人员可见范围 |
| `models/user.py`、`routes/auth_helpers.py` | 已有密码哈希；JWT 按本地用户 ID 查询 | 账号未备份；恢复哈希不能自动撤销旧 JWT |
| `frontend/src/components/admin/AccountSetBackupModal.tsx` | 单月、逐条下拉、全部冲突批处理 | 缺多月、完整类别选择及任意行勾选 |
| `services/migration_service.py` | 固定迁移表顺序 | 新快照表及账号状态字段必须纳入整库迁移 |

现有 ZIP 路径检查、SHA-256 校验、预览归属及有效期、目标指纹、数据库锁、文件暂存/清理和恢复审计应保留。不是重新建设另一套备份系统。

## 3. 数据分类与选择边界

### 3.1 用户可选择类别

| 类别 ID（拟定） | 内容 | 作用范围 |
| --- | --- | --- |
| account_settings | 账套业务参数、厂休 | 所选月份 |
| attendance | 日报、月报、逐日/月度修正、修正历史、同步历史 | 所选月份 |
| meal_tickets | 核算批次、明细、补扣、充值、冲正、历史导入记录 | 业务/源考勤月份，提示充值月 |
| meal_ledgers | 独立台账、取款/清零等记录、来源信息 | 台账业务月份 |
| archives | 上述类别所依赖的原始文件 | 随对应记录 |
| departments | 当前完整部门树及有效状态 | 全局共享 |
| employees | 当前完整人员及状态、卡号和统计来源配置 | 全局共享 |
| shifts | 当前完整班次、人员默认分配 | 全局共享 |
| accounts | 账号、哈希、状态、角色、页面权限、授权关系 | 全局共享 |
| cross_month | 请假、加班等跨月单据 | 明确列出涉及月份 |
| annual_stats | 年假余额、管理人员年度统计及手工/自动来源 | 明确列出年份及影响月份 |

月度快照作为月份业务的必要组成，不提供“恢复数据但丢弃其历史身份”的独立选项。归档依赖也不得通过取消 archives 造成悬空引用：取消时同时取消依赖记录或提示补选，不偷偷扩大恢复范围。

默认导出所选月份所有类别。导入类别初始建议为备份中实际包含的全部类别，跨月/年度条目必须在确认页单独列出；该导入初始默认是技术建议，不改变用户可以选择范围的要求。

### 3.2 完整当前资料与历史身份

当前资料退出有效集合使用独立有效状态，不借用 resigned_at、部门锁定或账号失败次数表达。人员离职仍是业务状态；“恢复后不属于当前资料”是另一个状态。

人员、部门、班次可保留内部行及稳定本地 ID，为历史外键服务，但不再出现在当前维护/新业务默认候选中。重导入相同业务编号时恢复原行，避免唯一键冲突和历史断链。界面确认使用“退出当前资料”，不误称物理删除。

账号可采用禁用/归档状态退出当前有效账号集合；旧用户 ID 不复用。历史操作审计保留操作者身份。不得导入源数据库自增 ID 作为本地 ID。

## 4. 历史隔离

### 4.1 建议快照结构

新增统一的月度资料快照表，建议模型 `MonthlyReferenceSnapshot`：

- month、kind（employee/department/shift）、business_key 联合唯一。
- payload：该月所需姓名、部门归属及部门树、人员类型、统计来源、离职状态解释、班次时段及默认分配等。
- provenance：归档提取、旧数据基线、正常月度采集或备份恢复。
- quality：verified（来源可证）、baseline（只保证改造后的稳定性）、partial（存在缺失）。
- schema_version：快照格式版本。
- created_at、updated_at：记录形成时间。

payload 不包含账号密码和权限；权限不是历史业务资料，访问仍执行当前授权规则，历史部门归属用快照计算，不因为冻结历史而冻结账号权限。

快照必须覆盖历史查询、报表导出、重算、菜票考勤来源、历史人员列表及按部门汇总实际使用的字段。不能只冻结姓名和部门名称。

### 4.2 形成与更新规则

- 初次建立月份业务时形成快照，之后编辑当前基础资料不自动刷新过去月份。
- 当月需要修正资料时，必须是明确针对该月的操作，更新该月快照及相关结果，不扩散其他月份。
- 恢复所选月的业务同时按选择恢复该月快照；未选月快照不变。
- 同月多个业务类别共享资料快照有冲突时，预览明确展示影响，不通过恢复菜票隐式改写未选考勤。必要时阻止选择并要求统一月度资料选择。
- 当前资料查询使用有效集合；历史业务查询由当月快照与当月记录确定人员，不再依赖当前在职筛选。

### 4.3 旧月份补齐

按归档文件、日报/月报原始字段、已有菜票快照核对历史信息。资料来源冲突时记录候选和来源，不静默选当前值。

可证字段保存为 verified；无法证明的字段可保存升级时的基线，标注 baseline，保证今后不会漂移，但不能宣称还原了真实过去状态。导出携带来源与质量，导入保留这些标记。

补齐应先提供只读扫描报告，再提供显式写入命令，重复执行幂等。禁止在生产环境自动删除或重算历史数据。

## 5. 备份格式 v2 与后续演进

建议 ZIP 结构：

```text
manifest.json
shared.json
months/2026-06.json
months/2026-07.json
cross_month.json
annual.json
files/<内容摘要或稳定文件键>
```

manifest 包含 format_version=2、实际应用构建标识（可为空但不能伪造）、导出时间、月份清单、类别及数据集版本、included/complete、完整共享范围声明、每个文件字节数和 SHA-256。files 路径与数据引用严格校验，继续拒绝路径穿越、重复成员和超限解压。

月度 JSON 包含账套参数、各月数据和快照；shared 当前资料只保存一份；跨月单据按业务键去重；年度资料按员工/年份/类型去重；相同文件内容可复用一个成员。

导出各份数据必须来自一致的数据库视图或通过全范围前后指纹验证；不能独立生成多个 v1 包后拼接，避免资料时间点不同。当前压缩上传限制为 100 MiB；v2 初期保留现有实际限制和明确报错，不擅自加入分卷或后台队列。

### 5.1 旧备份兼容

read_backup 将 v1/v2 都转换成统一内部文档。

- v1 只有一个月份，共享资料是关联子集：必须标记 complete=false，不能删除其他当前共享资料。
- v1 没有账号、完整月度快照或后来增加的类别：标记 included=false，禁止据此删除。
- v1 有部分类别但无法证明完整覆盖时，不启用按缺失删除，界面说明原因。
- v1 原有可恢复字段继续可用；缺少的历史快照标注质量，不补造可信历史。
- 删除默认只对 selected=true、included=true、complete=true 的范围成立。明确“空且完整”可清空，“未包含/不完整”不等于空。
- 未知更高版本阻止导入并给出支持范围，绝不尝试部分写入。

### 5.2 开发同步机制

统一类别/数据集注册表声明模型、字段、关系、业务键、范围、版本、选择类别与删除策略。对所有 ORM 表和字段执行覆盖检查，必须有备份映射或有理由的排除声明。

排除应细到字段：本地 ID、临时路径、登录临时锁定计数等可不迁移，但账号长期禁用状态需备份。排除模型逐一说明，例如消息并非本次确认的月度业务范围，预览任务是临时数据；不能用一条“其他表忽略”掩盖新增表。

AGENTS.md 加入规则：业务表/字段/语义变化时，检查导出、预览、恢复、依赖、版本迁移及旧格式测试；覆盖测试未通过不能宣称完成。

## 6. 差异与多选

每行使用稳定 row_key（scope + month/year + dataset + business_key）；密码行只显示一致/不同，不返回哈希。前端 choices 只传 server row_key 与 backup/system/skip，所有实际变更由服务端重建。

| 状态 | 默认 | 含义 |
| --- | --- | --- |
| new | backup | 新增备份独有记录 |
| changed | backup | 恢复备份字段 |
| system_only | backup | 在完整且被选范围内删除业务记录/退出当前资料 |
| same | system | 无变更 |
| absent/incomplete category | 不允许按缺失删除 | 保留目标未覆盖的数据 |

筛选包含月份、类别、差异状态、关键词。支持单行勾选、当前筛选结果全选、取消选择及批量采用备份/保留系统/跳过。全选明确数量和作用范围；隐藏行的已选状态显示出来，不把全部冲突当作当前筛选项。

使用分页或渐进渲染解决大清单，不默认渲染全部字段表。预览时清楚区分未选择、缺少依赖、锁定和不完整范围。

## 7. 最终状态、菜票及跨月恢复

预览先计算选择后的最终状态，再校验：人员所属部门、父部门、班次、卡号唯一性、账号授权目标，以及菜票批次/明细/补扣/充值/冲正关系。

允许用户选择恢复有差异的菜票历史，但只在最终关系与资金历史自洽时执行。不能把备份充值直接拼到不同核算快照，也不能删除原支付却保留指向它的冲正。缺依赖时显示具体行与“需要一并选择的记录”，由用户补选；不自动越过选择边界。

恢复本地记录不调用真实充值/扣款设备，不重放外部支付动作。保留业务幂等键与来源去重信息，恢复后常规业务操作不能再次计款。

跨月及年度数据使用明确选择清单，影响所选月份以外时在确认页突出列出。未选择的跨月/年度记录不执行缺失删除。账套锁定沿用当前规则：任何实际变更影响锁定月份时阻止，提示先解锁，不在备份功能内偷偷绕过锁定。

## 8. 账号恢复

账号自然键是 username；人员/部门授权使用业务编号映射。profile_dept_id、授权表外键和关联人员不照搬源 ID。支持数据库 ID 不同而业务编号相同的恢复。

密码哈希可导出至包，但预览 API、前端、日志和审计不得显示哈希。差异给出密码是否变化的布尔标记。旧 JWT 使用新增本地 auth_version 校验；恢复账号时递增受影响账号的本地版本，不导入源版本。保留至少一个可登录管理员，最终选择不能删除/禁用全部管理员。

允许当前操作者受恢复影响；事务完成后先返回结果，再结束其登录。恢复审计保存操作者用户名快照，避免当前账号退出有效集合导致审计失去含义。操作人员不得在恢复中被物理级联删除。

## 9. 事务、文件与审计

多月恢复统一预览、目标指纹、确认和数据库事务。按父先新增、子先删除顺序执行，处理卡号互换、部门树重排等唯一约束。

文件先写私有暂存位置，确认所有内容与引用后提交；失败撤销数据库并清理新文件，成功后通过现有清理日志处理旧文件，不提前删除仍被其他月份引用的文件。

审计保存备份摘要、月份清单、所选类别、最终选择摘要、每类别数量、操作者身份、时间及明确影响范围，不保存密码哈希。新增多月审计兼容现有单月记录；一次恢复有一个任务标识，不把多个独立提交假装成原子操作。

## 10. 不包含的范围

本方案不包含云端自动备份、定时任务、ZIP 密码加密、分卷、通用整站镜像或真实外部充值重放。数据库连接凭证、.env、JWT 密钥不作为普通业务备份导出。若后续需要这些内容，应单独确认。

## 11. 验收场景

1. 导出 6/7 月，导入只选 6 月考勤，7 月及未选类别数据不变。
2. 当月无考勤人员、空部门和未分配班次仍进入完整当前资料。
3. 当前恢复后人员转部门/离职，未恢复历史月份的查询、人员集合、部门汇总、下载和重算不漂移。
4. 多月包含同一跨月单据，只恢复一次；年度资料只影响明示范围。
5. 全量 v2 的系统独有默认移除；取消选择保留；v1 子集不能删除完整共享资料。
6. 菜票冲突可以选择备份，完整一致状态可恢复，不完整的资金关系被阻止。
7. 新库恢复账号可用旧密码登录，源/目标 ID 不同的权限映射正确，旧 JWT 失效。
8. 多月中任一数据/文件写入失败，全部月份和账号状态回滚，目标原文件仍可用。
9. 新增未登记业务字段时覆盖检查失败；旧包没有该字段/类别不会触发误删。
10. 预览没有修改数据；过期、他人任务、已完成任务和目标变化均拒绝执行。
