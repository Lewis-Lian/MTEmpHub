# 菜票中心第一期设计规格

状态：第一期已按用户确认范围实施。日期：2026-10-08。

## 1. 目标与范围

面向管理员，将现有员工、管理人员考勤结果转为可核对、可调整、可导出、可登记实际充值的月度菜票账；查询账号按已有人员/部门授权查看数据。

用户已确认的规则：

- 严格采用现有“实际打卡天数”字段最终值。菜票中心不定义、解释或重新计算单日打卡计天规则。
- 基础补贴 = 实际打卡天数 × 8 元；不另算天数、不四舍五入天数、不自动扣异常次数。
- 当月考勤的补贴在次月充值：2026-08 考勤对应 2026-09 充值，12 月考勤对应次年 1 月充值。
- 保留额外情况手工补扣。
- 部门金额是人员充值金额的汇总，由人员明细生成，不重复入账。

第一期交付：月度核算、依据查看、额外补扣、人员和部门 Excel 导出、实际充值确认、历史人员原账导入和部门对账。
外来人员发放、历史取款分类、消费统计和完整年度汇总留在后续；第一期不连接真实充值设备，不推算个人卡余额。

## 2. 架构与考勤取值

沿用 Flask / SQLAlchemy 后端与 React / TypeScript 前端。新增独立菜票模块，不将充值金额写入考勤表。

| 人员 | 复用结果 | 禁止混用 |
| --- | --- | --- |
| 普通员工 | 员工查询的 actual_attendance_days，包含现有月度覆盖 | 普通出勤天数、日历展示值重新累加 |
| 管理人员 | 管理人员查询的 punch_days | 管理人员 actual_attendance_days（实际出勤天数） |

基于 Employee.is_manager 选择上述结果，复用该查询的考勤来源配置；include_in_manager_stats 不生成第二笔补贴。每人每考勤月只有一条正式核算明细。
从查询逻辑中提取必要的共享汇总入口，查询和菜票共同调用；不得请求自身 HTTP API 或复制计天算法。

缺少所需考勤来源与正常零天区分：缺来源显示“待核对”，不能确认为可发放明细。若人工月度覆盖已经给出合法最终值，则保存其修正依据。负数、非有限数或超过当月自然日数的天数显示字段异常，先修正考勤再核算。

第一期不能还原员工历史部门，生成草稿时使用现有部门并保存快照。页面明确显示“核算部门”；管理员确认前核对归属。确认后员工调部门或改名不改变旧账展示。

## 3. 月份和金额

保存三个独立时间字段：考勤月份、计划充值月份、实际充值日期。源账套关联考勤月份，计划充值月份由考勤月份加一个自然月得到。
页面默认按计划充值月份选择，旁边持续显示对应考勤月；不得因当前激活账套变化而更换已选择的来源月份。

金额公式：

- 基础金额 = 字段天数 × 8 元。
- 应发金额 = 基础金额 + 有效额外调整合计。
- 净已发金额 = 实际充值金额 − 已确认的扣回金额，扣除已冲正记录的影响。
- 差额 = 应发金额 − 净已发金额。正值待补发，负值待扣回，零为结清。

金额以整数分保存，以 Decimal 计算，基础金额按分四舍五入，天数本身保持字段值。调整允许正负金额，最多两位小数，不要求为 8 的倍数。应发金额小于零时阻止核算确认和新充值，提示检查调整。

部门报表按同一集合的人员快照分组，分别求和基础、调整、应发、净已发、差额。没有部门的人员单列“未分配部门”。查询账号的汇总仅包含其可见人员。

## 4. 页面与操作

导航新增“菜票中心”，包含三个页面：

1. **月度核算**：选择充值月，显示考勤月；生成/重算草稿；筛选员工、管理人员、部门和核对状态。列表显示工号、姓名、核算部门、实际打卡天数、基础金额、补扣、应发和核对状态。展开可查看考勤来源、月度修正说明、原考勤链接及调整历史。
2. **充值与对账**：显示应发、净已发、差额及未发/部分发/结清/待扣回状态；按人或勾选人员登记实际充值，可按剩余待发额批量登记。单独提供扣回与错误记录冲正操作。
3. **历史台账**：上传、预览、映射、确认导入；查看原账人员数据与部门汇总差异。原账金额和新规则试算金额分别展示。

导出为一个工作簿，包含人员明细和部门汇总两个工作表，标明两个月份、生成时间及草稿/已确认状态。人员明细含工号、姓名、部门、打卡天数、基础金额、调整、应发、净已发、差额和备注。导出草稿需显著标注“草稿”，导出不会自动产生充值记录。

## 5. 确认、调整与实际充值

核算批次只有草稿与已确认两个状态，结清状态从人员金额派生，不额外维护整月“已发”标志。

- 草稿可重算，保留人员补扣；若来源变化导致人员移出或无效，保留该人员调整并标记待核对，不能静默丢失。
- 确认前要求源考勤账套已锁定；重新校验人员范围、最终字段和来源说明是否与草稿一致。变化时返回冲突，管理员刷新重算后确认。
- 已确认批次冻结天数、基础金额、人员和部门快照。尚无任何充值、扣回或冲正流水时，管理员可从“导出充值表”步骤退回草稿，清除确认人及确认时间并递增批次版本；保留明细、补扣及本月不发选择，不自动解锁考勤账套。退回后须重新确认及导出，旧充值表不再使用；外部已实际充值时应先登记流水。存在任意发放流水时禁止退回，包括已冲正且净已发为零的情况。
- 调整须填写原因，记录操作人和时间。确认前更正调整也用追加反向记录和正确记录实现，保留历史；确认后允许追加调整，不解锁或修改考勤字段。
- 源账套后来解锁或考勤发生变化，只提示源数据变化；管理员核对后通过额外补扣处理差额，不自动改账。
- 实际充值只能登记到已确认的人员明细，金额必须大于零且不超过待发金额；扣回必须大于零且不超过待扣回金额。
- 实际日期必填，凭证编号/说明必填，备注可选。未真正完成的充值不能登记为已发。
- 错误发放记录只能冲正一次，冲正须写原因；金额相反的修正记录引用原记录，原记录保留。重新登记为新记录。
- 修改与确认采用批次版本校验；发放请求使用唯一请求标识防重复，并在同一事务中锁定明细、重新检查剩余金额。相同标识和内容重试返回原结果，不同内容重用标识返回冲突。

## 6. 数据模型

| 表 | 关键数据和约束 |
| --- | --- |
| meal_ticket_batches | 源账套、考勤月（唯一）、充值月、规则版本、800 分标准、状态、版本、生成/确认人和时间 |
| meal_ticket_items | 批次、员工 ID、工号/姓名/部门快照、人员类型、来源说明、字段最终天数、基础金额；批次+人员唯一 |
| meal_ticket_adjustments | 人员明细、金额分、原因、操作人/时间、可选被反向调整记录；不硬删除 |
| meal_ticket_payments | 人员明细、充值/扣回/冲正类型、金额分、日期、凭证、操作人、唯一请求标识、可选原记录引用 |
| meal_ticket_imports | 文件校验值、归档路径、状态、月份映射、导入人/时间；同文件同映射防重复 |
| meal_ticket_import_rows | 导入批次、页名/行号、人员原字段与原公式/金额、匹配人员/部门、明确的考勤月/充值月、核对状态和错误 |

源文件留在上传归档目录。历史部门对账行也使用导入行保存，行类型区别人员和部门汇总；部门行不参与人员金额合计。
正式核算与历史原账分别保存，同月可比较而不相加。历史原账导入不会自动创建实际充值记录。

## 7. 历史导入与对账

按列标题识别员工充值、管理人员充值/查询和部门登记表，限定人员区域，排除右侧透视汇总、总计行和空白页。上传与确认分两步，预览列出有效、异常、重复和未匹配行。

- 工号按文本保存并匹配；卡号辅助核对。仅凭姓名不自动关联。未匹配人员保留原账行，管理员可映射到现有人员，导入不自动创建员工。
- 部门保留原名，由管理员确认映射；数字部门值不自动解释为部门 ID。
- 文件月份含义由导入者明确选择“考勤月”或“充值月”，系统推导另一个月份并供核对。页内年份冲突要求逐页确认。
- 公式同时保留原文和有效缓存结果，不能假定读文件会计算 XLOOKUP。错误值或缺缓存必须手工提供金额并保存更正说明，或明确跳过该行；未解决行不作为零导入。
- 同月同工号出现在多个人员页时展示冲突，不叠加金额。不同文件与已导入原账冲突时预览差异；第一期保留旧账，冲突行不能覆盖，须跳过。
- 部门历史原额与匹配月份的人员原账部门合计逐项比较，保留差额，不自动修正任一边；总额包含未匹配人员并单列其金额，不能因匹配失败少计金额。
- 用户指定的 9 月充值文件为空，不产生零金额月份或已发记录。历史取款和外来人员页面提示本期不支持，不能按人员充值页误导入。

## 8. 权限、备份和既有操作

管理员可生成、调整、确认、登记、导入；查询账号需新增 meal_ticket_query 页面权限，并沿用既有人员/部门数据范围。所有读接口、汇总、导出与详情一致执行权限检查。

模块接入 utils/app_navigation.py、前端受保护路由和后端蓝图。数据库增量迁移同时覆盖 SQLite/MySQL；初始化/旧库升级注册新增模型。

新增数据按外键顺序进入切库迁移清单。账套备份按考勤月包含批次、明细、调整、充值及该月历史原账和源文件；实际充值日期在次月也须随源考勤账套备份。
恢复沿用差异预览和版本校验。实施采用保守保护：已存在的菜票记录（含草稿）均不允许通过恢复覆盖或删除；仅补入缺失且一致的记录。补入发放必须与保留的已确认核算快照及金融历史一致，避免拼接不同账目。目标考勤账套仍遵守现有恢复解锁要求。

存在正式菜票明细或已关联历史原账的人员禁止单条/批量硬删除，改用现有离职操作。存在菜票批次的账套禁止删除；部门删除不删除明细快照。不得修改无菜票关联时的既有删除行为。

## 9. 验收标准

1. 员工/管理人员金额等于各自已配置的打卡字段最终值 × 8；月度人工覆盖被复用，没有额外异常扣款。
2. 菜票取值与现有“实际打卡天数”字段最终值一致，不根据单日打卡次数推算或覆盖；兼属两类统计范围只生成一条核算明细。
3. 9 月充值读取 8 月考勤，跨年同样正确；导出和页面两个月份一致。
4. 22 天、+16 元调整得应发 192 元；发 176 元后待补 16 元。追加 −24 元后应发 168 元、待扣回 8 元，扣回后结清。
5. 调整不能改考勤字段；重算草稿不丢调整；确认后重算被拒绝，源数据变化可见。无发放流水的确认可由管理员退回草稿；已有流水或版本过期时退回被拒绝，退回后导出及发放需重新确认。
6. 同请求重复发放不新增记录，并发请求不超发；冲正只能一次，重试不重复冲正。
7. 部门合计等于相同范围人员总额，人员调整自动更新汇总；历史部门行不会增加发放总额。
8. 缺来源、字段异常、缺公式缓存、重复人员、未匹配和月份歧义均明确显示，不能伪装成正常零金额。
9. 历史原账保留旧金额/公式；导入预览不写业务账，重复导入不重复记账。
10. 受限账号不能查询或导出范围外人员；备份恢复和 SQLite/MySQL 切库保留新增数据，已发历史不会被覆盖；人员和账套删除有明确关联提示。

## 10. 交付边界

实施覆盖数据模型与共享考勤读取、核算与发放接口、前端页面和导出、历史导入、权限与备份迁移。未扩展第二期业务；未自动导入用户原始文件或连接真实充值设备。
